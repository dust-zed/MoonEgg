此文档围绕一个核心问题：

> 同一个媒体时刻的声音和画面，怎样在现实世界中同时呈现？

### 第 1 章：音视频同步，究竟在同步什么？

#### 1.1 同步的是“呈现”，而不是“处理速度”

假设电影第 10 秒，画面里有人拍手，同时音轨里有拍手声。
正确的目标是：
- 用户看到双手接触；
- 用户听到拍手声；
- 两件事尽量同时发生。
它不要求音频和视频同时解码，也不要求两者同时进入输出队列。
实际上，两条路径可能很不一样：

```
音频：读取 → 解码 → 缓冲 → 音频设备 → 声音
视频：读取 → 解码 → 渲染 → 显示刷新 → 画面
```
因此：
处理完成时间、提交时间、实际呈现时间，是三个不同的概念。
提前解码并缓存下一秒的内容，完全正常。同步控制关心的是这些内容最终什么时候呈现。

#### 1.2 PTS告诉我们“这份内容属于哪里”
PTS，即呈现时间戳，可以先理解为：
> 这份音频或画面，应该在媒体时间轴的哪个位置呈现。

例如：
```
视频帧 PTS：10.000 秒
音频片段起点 PTS：10.000 秒
```
它们描述的是内容的位置，并没有告诉我们现实世界中什么时候到达“电影第 10 秒”。
所以播放器还需要一个会前进的播放时钟。
可以把两者的关系记成：

```
PTS: 这份内容应该在什么时候呈现？
播放时钟：现在已经播放到什么时候？
```

把两者放到同一时间坐标里比较，才有可能完成同步。GStreamer 的同步模型也是把内容时间戳和时钟运行时间进行映射后再比较。

### 第 2 章：单调时钟提供什么？
#### 2.1 它首先是一把测量时间间隔的尺子
单调时钟适合回答：
> 从刚才那个时刻到现在，经过了多久？
它不像日历时间那样，因为用户修改了系统时间，就突然跳到昨天。
但它本身不知道：
- 你正在播放哪部电影。
- 从电影第几秒开始；
- 是否暂停了；
- 当前是正常速度还是二倍速。
这些都需要播放器建立映射。

#### 2.2 从单调时间建立媒体时间
假设：
- 从媒体第 30 秒开始；
- 开始时的单调时刻是\(t_0\)；
- 播放速度为一倍速；
- 中途没有暂停。

那么：
\[
M(t)=30+(t-t_0)
\]

这里：
- t：当前单调时刻；
- M(t): 根据经过时间推算的媒体位置。

例如：
| 实际经过的时间 | 推算的媒体位置 |
|---:|---:|
| 0 秒 | 30 秒 |
| 0.5 秒 | 30.5 秒 |
| 2 秒 | 32 秒 |

如果播放速度为 r，就变成：
\[
M(t)=M_0+r(t-t_0)
\]

这就是一个典型的“根据单调时间推进媒体时间”的模型。

#### 2.3 它给出的，是播放计划
这个公式非常重要，但也有一个前提：
**它假设输出过程能够跟上这个播放计划**
公式算出“现在应该到 32 秒”，不能自动证明：
- 音频设备真的输出到了第 32 秒；
- 视频第 32 秒的画面已经现实；
- 相关数据已经及时解码出来。

时钟继续走，输出设备却可能延迟、缺数据或运行节奏略有不同。
这就是为什么还需要观察输出进度。

### 第 3 章：音频时钟提供什么？
#### 3.1 音频时钟把输出进度映射到媒体时间
音频输出设备或持续消耗 PCM 数据。
播放器可以根据设备提供的播放位置、输出时间或延迟估计，计算当前音频对应的媒体位置。
这个结果通常被称为音频时钟。
它主要回答：
> 按照音频输出端的观测，声音现在播放到媒体的那个位置？
它是一种计时依据，并不意味着必须额外启动一个“音频计时线程”。读取设备信息并做时间换算，也可以构成音频时钟。

#### 3.2 音频帧数怎样变成时间？
在正常一倍速、固定采样率、连续音频的简化条件下：
```
A = M_0 + (N - N_0) / f_s
```
其中：
- A： 音频媒体位置；
- M_0: 媒体时间锚点；
- N：当前呈现的音频帧位置
- N_0：锚点对应的音频帧位置；
- f_s：与这个帧计数对应的采样率。

假设：
```
媒体时间锚点：30 秒
帧计数锚点：100,000
当前帧计数：148,000
采样率：48,000 Hz
```

那么：
```
新增播放帧数 = 48,000
对应时长     = 1 秒
音频媒体位置 = 31 秒
```

#### 3.4 "已经提交" 不能直接当成“已经播放”
假设队列中提前放入了 200 毫秒的音频：
```
队列末尾对应的媒体时间：10.200 秒
设备当前呈现的媒体时间：10.000 秒
```
如果用队列末尾当音频时钟，视频就可能领先声音约 200 毫秒。
因此，音频时钟可能需要结合播放指针和缓冲延迟计算，而不能只看提交的数据量。
同时，设备报告的位置和时间也有测量边界。某个接口可能描述音频管线中的位置，并不直接测量声音到达耳朵的时刻。
平台不知道的延迟，也无法自动补偿。

**所以音频时钟提供的是依据输出观测建立的媒体进度，精度取决于观测能力与延迟处理。**

### 第 4 章： 两种时钟为什么会不一致？
这一章是理解音视频同步的关键。先把问题分成两类：**时间偏移和速率偏差**。

#### 4.1 时间偏移：两者的起点没有对齐

考虑一个教学例子：
* 播放器按单调时间立刻安排视频；
* 音频经过设备启动和缓冲，晚了 150 毫秒开始；
* 此后两边都按相同速度运行。

经过 1 秒时：

| 对象 | 媒体位置 |
|---|---:|
| 按单调时间播放的视频 | 1.000 秒 |
| 实际输出的音频 | 0.850 秒 |

画面领先了声音。

这里单调时钟没有计错时间，问题出在两条输出路径的起点没有对齐。
如果这段延迟固定且已知，可以通过安排共同的呈现起点或延迟补偿解决。音视频管线需要考虑各条路径的延迟，而不是要求各条路径本身没有延迟。

也要注意：
> 声音和画面一起晚了 500 毫秒，仍然可能完全同步。
  声音和画面之前相差 150 毫秒，才是这里讨论的同步问题。

#### 4.2 速率偏差：起点对齐了，之后却越走越远
系统计时基准与音频设备的输出节奏，可能存在细微差异。

例如，标称 48,000 Hz 表达的是音频格式和预期速率。不能仅凭这个数字，就断言音频设备相对于系统时间的实际运行速度永远毫无误差。
假设两个时间基准的速率相差 0.01%，那么：
```
播放 1 小时后的累计偏差：
3600 秒 × 0.0001 = 0.36 秒
```
这是数学示例，不是某种设备的实测指标。
它说明了一个问题：**启动时对齐一次，不代表长期都能保持对齐**。
时钟校准通常需要同时处理起点偏移和运行速率差异。

#### 4.3 这两类问题需要不同的修正

| 问题 | 表现 | 处理方向 |
|---|---|---|
| 时间偏移 | 始终相差一段时间 | 调整起点或延迟补偿 |
| 速率偏差 | 播放越久，差得越多 | 持续校准、调整跟随速率 |
| 临时中断 | 某一路突然跟不上 | 缓冲、等待、丢弃或重新同步 |

"单调"保证的是时间顺序，它没有承诺其他设备一定按照同样的节奏运行。

### 第 5 章：主时钟到底是什么？为什么常选音频？

#### 5.1 主时钟是一种角色
主时钟表示
> 当不同输出的进度不一致时，以哪个时间基准作为同步参考？
它可以来自:
- 音频输出进度；
- 系统计时建立的媒体时间；
- 视频呈现进度；
- 某种外部同步时间。

所以，“使用音频时钟”和“使用单调时间”并不是非此即彼的物理分类。
例如，音频时钟也可以利用单调时间计算两次设备观测之间的进度。

#### 5.2 音频为主：视频跟随音频

假设音视时钟为 10 秒：
| 视频帧 PTS | 基本决策 |
|---|---|
| 10.080 秒 | 等待 |
| 10.000 秒 | 安排呈现 |
| 9.700 秒 | 根据迟到程度决定是否丢弃 |

这里省略了显示延迟和容差，目的是说明决策依据。
为什么这种方案常见？
音频是连续波形。直接跳过或重复一段音频，可能带来明显的声音断裂或内容缺失。
视频则可以通过延长当前画面的显示时间、跳过过时帧等方式调整进度。视频调整也会影响体验，但控制手段通常更直接。
因此，许多播放器选择让视频跟随音频。ffplay 支持音频、视频和外部时钟作为主时钟，默认使用音频。
