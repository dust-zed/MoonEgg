# Rust 调试指南：从定位现象到验证修复

更新：2026-09-23。

面向正在学习 Rust 调试的开发者。主线使用 LLDB，覆盖本地程序、测试、异步与多线程，以及 Android 中的 Rust 原生库。本文不依赖特定项目或某一次故障。

示例中的包名、程序名、路径、行号、PID 都需要替换。终端命令采用 macOS/Linux 的 shell 写法；Windows 的可执行文件后缀、环境变量和调试器集成方式不同。

## 1. 调试首先要回答什么

调试不是立即解释“为什么错”，而是逐步建立证据：

1. 预期行为是什么，实际行为是什么？
2. 哪组输入和操作能够复现？
3. 程序第一次偏离预期发生在哪里？
4. 那一刻的输入、状态和调用路径是什么？
5. 哪个假设能够解释这些事实，怎样验证它？
6. 修复后，同样的复现步骤是否通过？

错误显示的位置、错误产生的位置和根因所在的位置，可能是三个不同的地方。例如界面显示失败，工作线程返回错误，而根因是更早的一次错误状态更新。

记录时分开写“事实”和“假设”。“重试后成功”是事实；“一定是线程竞争”只是解释之一。

## 2. 先判断问题属于哪一类

| 问题 | 首选检查方式 | 不应混淆的点 |
|---|---|---|
| 编译错误 | 第一条相关诊断、类型与条件编译配置 | 编译尚未成功，运行时断点无法帮助 |
| 普通 `Result::Err` | 错误返回分支、调用栈、输入 | 返回 Err 不自动触发异常断点 |
| `panic!` / 越界 / `unwrap` 失败 | panic 信息和回溯，必要时断点复现 | panic 不等同于普通 Err |
| 原生崩溃 | 信号/异常、崩溃线程、匹配符号 | 当前崩溃行可能只是更早内存破坏的受害者 |
| 卡住或死锁 | 多次线程栈快照、锁与等待关系 | 一次停在等待函数里不能证明死锁 |
| 输出错误但没有报错 | 数据流与不变量，在结果变错前后比较 | 没有错误返回，也可能有逻辑错误 |
| 偶发、超时、性能问题 | 低干扰事件记录或性能采样，辅以断点 | 暂停会改变时序，单步可能改变现象 |

工具选择依据是问题特点。容易稳定复现的逻辑错误，通常可以先下断点；只在连续运行中出现的问题，日志或追踪可能更合适。

## 3. 理解调试器、符号和源码

调试器操作的是进程中的机器码。源码行号和变量名称来自编译时生成的调试信息。

```text
源码
  │ 编译与链接
  ▼
可执行文件 / 动态库 ── 含有或关联调试信息
  │ 加载
  ▼
运行中的进程
  ▲
  │ 调试器连接，匹配模块与调试信息
LLDB / GDB / IDE 的调试后端
```

需要分别确认：

- 连接的是正确进程。
- 目标模块已加载，并被调试器识别。
- 符号文件与正在执行的机器码来自同一次构建。
- 源码路径与版本匹配。

函数导出符号、完整调试信息、构建标识不是一回事。能找到一个 FFI 函数，不代表能查看函数内部所有 Rust 变量；有 Build ID，也不代表保留了源码调试信息。

## 4. 准备可调试的构建

先使用项目现有的开发构建，通常不必一开始修改配置：

```bash
cargo build -p my_package --bin my_app
```

Cargo 默认 dev 配置保留完整调试信息且不启用优化。若项目覆盖了 profile，应检查 `debug`、`opt-level`、`strip` 和平台的独立符号文件。Workspace 的 profile 在根清单配置。[Cargo profile 文档](https://doc.rust-lang.org/cargo/reference/profiles.html)

若故障只出现在优化构建，应保留能复现的构建条件，再增加调试信息。把 release 全面切换成 dev，可能连问题一起改变。

每次复现记录：源码版本、未提交修改、feature、目标平台、构建模式、启动参数、工作目录、必要环境变量。

重新编译后，要重新运行或部署新产物。不要拿刚编译的新符号解释仍在运行的旧程序。

## 5. 启动或附加调试器

### 5.1 本地命令行程序

下面假设构建输出是 `target/debug/my_app`。自定义 target 目录或交叉编译时，以实际产物路径为准。

在终端执行：

```bash
rust-lldb target/debug/my_app
```

`rust-lldb` 是 Rust 工具链提供的 LLDB 启动包装，底层仍需可用的 LLDB。若环境未提供它，可使用已有 IDE 的 Rust 调试配置或 LLDB，不必为一次定位迁移编辑器。

进入 LLDB 后执行：

```text
breakpoint set --name main
run
```

如果程序需要参数，可在启动时传入：

```text
run --input sample.dat
```

`run` 后面的参数是应用参数。确认工作目录与普通运行时一致，否则相对路径、配置文件或输入文件的差异会制造新问题。

### 5.2 已在运行的程序

使用 IDE 的 Attach 功能，或在独立 LLDB 会话执行：

```text
process attach --pid 12345
```

替换 PID。附加权限受操作系统限制；失败时读取具体错误，不要把权限问题解释为程序内部故障。

### 5.3 Rust 动态库

动态库通常不能作为普通程序直接 `run`。应启动或附加加载它的宿主进程，例如 Android 应用、Python 进程或测试程序。

电脑上的源文件属于哪个目录，不决定应该附加哪个进程；机器码实际在哪里执行，才决定调试目标。

## 6. 先学会暂停、检查和继续

| 操作 | LLDB 命令 | 用途 |
|---|---|---|
| 进程状态 | `process status` | 确认正在运行还是已停止 |
| 暂停 | `process interrupt` | 适用于可接受此命令的会话；IDE 也有 Pause 按钮 |
| 调用栈 | `bt` | 当前线程如何到达这里 |
| 局部变量 | `frame variable` | 当前栈帧中的变量 |
| 指定变量 | `frame variable value` | 缩小输出 |
| 切换栈帧 | `frame select 2` | 查看调用者或其他层的上下文 |
| 单步跨过 | `next` | 执行下一步，通常不进入被调函数 |
| 单步进入 | `step` | 尝试进入调用 |
| 执行到返回 | `finish` | 继续执行直到当前函数返回 |
| 恢复运行 | `continue` | 运行至下一次暂停事件 |

`frame select` 只改变观察位置；`next`、`step`、`finish` 和 `continue` 会让程序实际执行。没有启用专门的记录机制时，切换栈帧不能让程序回到过去。

这些命令及断点语法参见 [LLDB 教程](https://lldb.llvm.org/use/tutorial.html)。

IDE 控制台的输入规则可能不同。如果运行时面板只读，先使用 IDE 的 Pause Program，再输入命令。不要据此推断所有 LLDB 控制台运行时都无法输入。

## 7. 如何选择第一个断点

优先选择能够区分不同解释的位置：错误构造分支、无效状态分支、错误结果刚出现的位置。

例如：

```rust
fn checked_divide(total: u32, count: u32) -> Result<u32, &'static str> {
    if count == 0 {
        return Err("count must be positive");
    }
    Ok(total / count)
}
```

若现象是返回这个错误，第一个断点应放在 `return Err(...)`，而不是为每次函数调用都停下来。

```text
breakpoint set --file src/calculate.rs --line 42
breakpoint list
```

示例中的 42 必须替换成实际错误分支行号。命中后检查：

```text
frame variable total count
bt
```

如果确认 count 为零，下一步是检查调用者怎样得到它。断点证明了直接失败条件，但根因可能仍在上游。

检查 `breakpoint list` 是否解析到地址，以及地址对应的实际源码行。`0 locations` / pending 不等于代码没有执行。调试器也可能把断点移到邻近的可执行行。

对于频繁调用的位置，可以考虑条件断点或命中次数过滤。但 Rust 条件表达式的支持取决于调试器；复杂条件不能直接照搬成 Rust 代码后假设会工作。

## 8. 读懂调用栈与变量

调用栈描述当前线程上仍然存在的函数调用。最上面通常是暂停位置，往下是调用者。

读取顺序建议：

1. 当前帧：哪个判断失败，关键输入是什么？
2. 调用者：为什么会发起这个调用？
3. 更高一层：输入来自用户、配置、队列还是其他线程？

某个函数已经返回 Err 后，它的栈帧通常不再存在。在错误显示层暂停，未必能看到最初产生错误的函数。此时根据现有证据，把下一轮断点向上游移动。

变量显示 `optimized out` 不表示变量为空，而是当前机器码和调试信息不足以恢复它的值。Rust 的枚举、泛型、闭包和 Future 也可能以底层结构展示。

先用 `frame variable` 读现有数据，再考虑表达式求值。调试器里执行方法可能改变状态、获取锁或分配内存，不能默认是纯观察。

## 9. 分别处理 Err、panic 和原生崩溃

### 普通 Err

`?` 的作用是传播错误，不会自动保存“错误产生时的栈”。先在错误分支捕获，再看调用链。若错误在多个层次变得难以区分，之后可以为关键边界补充操作名和必要上下文。

### panic

在 macOS/Linux 终端可先运行：

```bash
RUST_BACKTRACE=1 cargo run -p my_package --bin my_app
```

从回溯中找到与你的代码相关的帧，并检查触发条件。需要更多栈信息时可使用 `RUST_BACKTRACE=full`。回溯可用性与符号和运行环境有关；自定义 panic hook 可能改变输出。这个环境变量不会自动给所有普通 Err 记录调用栈。[Rust panic 文档](https://doc.rust-lang.org/book/ch09-01-unrecoverable-errors-with-panic.html)

### 原生崩溃

先保留信号或异常类型、出错线程、地址和调用栈。不要立刻继续运行覆盖现场。

涉及 unsafe、FFI 或原生依赖时，要检查指针有效期、长度、对齐、所有权、线程约束和 ABI。机器指令崩溃的位置可能晚于最早的内存破坏；必要时再采用适合平台的内存检测工具。

## 10. 调试测试

先把问题缩小到已有的相关测试，而不是立即运行整个测试集：

```bash
cargo test -p my_package test_name -- --nocapture
```

`test_name` 默认是过滤条件，可能匹配多个测试。需要精确匹配时，使用完整测试名并加 `--exact`。

IDE 若支持调试单个测试，可以直接使用。手动操作时先构建测试可执行文件：

```bash
cargo test -p my_package --no-run
```

找到输出中的目标测试可执行文件，将其作为 LLDB 的调试目标。进入 LLDB 后用测试参数启动，例如：

```text
run module::test_name --exact --nocapture
```

测试运行器、普通 bin 和 example 可能是不同可执行文件。不要因为同属一个 crate，就认为当前调试目标一定包含目标测试。

## 11. 多线程、异步和超时

对于卡住的问题，先收集所有线程：

```text
thread list
thread backtrace all
```

观察谁持有资源、谁等待资源、是否存在循环等待。隔一段时间继续运行并再次暂停，可区分持续计算、偶然等待和稳定阻塞。

单个线程的栈不能跨越消息队列还原完整业务链。异步任务在 await 处挂起后，也不会一直占据当前线程的普通调用栈。必要时用请求 ID、任务 ID 或状态事件关联不同执行阶段。

**调试暂停会改变时序。** 进程停止时，系统时钟、其他进程、设备或远端服务可能继续前进。恢复后出现超时，不一定是原来的故障。

时间敏感问题可以优先在“已经判定失败”的分支捕获。若要观察连续状态变化，采用少量时间戳与状态记录；仍需注意日志本身也会增加开销。

不要把“断点下问题消失”视为已修复，也不要只因超时就增加期限。

## 12. Android 中的 Rust 原生库调试

### 连接路径

1. 使用可调试的 Android 构建，开启真机调试并授权电脑。
2. 启动宿主应用，等待初始化完成。
3. 在 Android Studio 使用 Attach Debugger to Android Process，选择正确包名和进程。
4. 只调 Rust 时选择 Native；同时调 Kotlin/Java 时选择 Dual。
5. 暂停后使用 LLDB 检查进程和模块。

具体菜单与调试类型参见 [Android Studio 官方说明](https://developer.android.com/studio/debug)。Rust 库若由外部工具构建，IDE 自动识别不一定完整。

### 验证模块

```text
process status
target list
image list -f
image lookup -n your_exported_function
```

`app_process64` 是 Android 应用的进程入口，并不应该被 Rust 库名替代。查动态库看 image list；查当前调用路径看 bt。

如果已有充分证据证明 Rust 功能正在执行，但模块列表没有库，就把问题定位在调试器的发现、获取或识别阶段，而不是继续猜测未调用 Rust。

用 adb 核对 PID，必要时通过应用身份读取进程映射。下面的包名和 PID 都是占位示例：

```bash
adb shell pidof com.example.app
adb shell run-as com.example.app cat /proc/12345/maps
```

`maps` 包含映射范围、权限、偏移与文件路径；读取权限失败是独立问题。[Linux /proc 文档](https://docs.kernel.org/filesystems/proc.html)

排查时依次核对：

- 手机 ABI 与构建目标是否一致。
- 当前进程加载的是否是刚部署的版本。
- 库是独立文件，还是直接从 APK 映射。
- 调试器能否读取文件并识别 ELF 模块。
- Build ID / UUID、符号文件及源码是否匹配。

缺少 Build ID 是一种可检查的情况，不是所有模块缺失的通用答案。直接从 APK 加载也不必然导致调试失败。每次只验证一项变化。

添加符号文件、添加调试器模块和在应用进程中加载库，是不同操作。不要只为了让列表出现库名就手动添加模块，然后误以为运行地址已经正确关联。

## 13. 常见现象如何解释

| 现象 | 先检查 |
|---|---|
| 控制台只读 | 选中的会话、连接状态、是否需要先暂停、输入区位置 |
| 断点始终 pending | 模块是否加载、符号是否匹配、源码路径及行号 |
| 有函数名但没有源码行 | 调试信息是否保留或可找到 |
| 单步跳行或变量不可见 | 编译优化、内联、宏展开、调试信息完整性 |
| 改过代码但执行结果没变 | 构建产物、部署目标和运行进程是否更新 |
| 正常运行有错，调试时没错 | 时序改变、构建模式变化、输入和环境差异 |
| 出错的是某个系统等待函数 | 是否只是手动暂停位置，真正错误是否已发生 |
| 错误在界面显示但栈里没有调用者 | 是否已经跨越线程、队列、异步边界或返回路径 |

## 14. 验证修复并形成记录

修改应对应已经建立的解释。用原来的输入、操作节奏和环境重新复现，再补充与该缺陷有关的边界验证。

能稳定表达缺陷的纯逻辑问题，适合留下回归测试；依赖设备或时序的问题，应同时保留复现条件和设备信息。一次未复现不能证明偶发问题已经根除。

完成后检查临时断点、日志和调试配置，保留有长期诊断价值的内容，避免把调查过程全部堆入产品逻辑。

```text
问题现象与预期：
环境 / 源码版本 / 构建方式：
复现输入、操作与频率：

第一个确认偏离预期的位置：
关键变量与调用栈：
已经确认的事实：
尚待验证的假设：

验证假设的方法与结果：
根因：
修复内容：
原复现步骤的验证结果：
相关边界或回归测试：
剩余限制：
```

## 15. 建议的练习顺序

1. 在本地小程序中设置行断点，查看参数并恢复运行。
2. 增加两层函数调用，练习 bt 和 frame select。
3. 对一个返回 Err 的分支定位输入来源。
4. 对一个 panic 阅读回溯，并在源码处复现。
5. 调试单个测试，确认启动参数与目标文件。
6. 查看多线程程序，练习区分正常等待和阻塞。
7. 最后练习 Android 或其他宿主进程中的原生库调试。

每一步都以“能解释看到的状态”为完成标准，而不只是记住命令。
