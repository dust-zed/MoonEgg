## 播放会话
播放会话管理，主要解决的是：
> 这一次播放需要哪些资源，谁拥有它们，哪些操作可以复用它们，什么时候必须清理，以及旧工作的结果还能不能影响当前播放。
它比“线程怎么退出”多了一层业务含义。当前最集中体现这层设计的是`PlaybackEffectExecutor`。
这里的设计取舍，主要体现在资源边界、所有权和异步时序上。

### 1. 播放会话指什么
当前代码没有专门定义`PlaybackSession`结构体，但已经有会话的概念：
```
一次 Prepare 创建 worker 和 pipeline
    ↓
使用这组资源完成播放、暂停、Seek、重播
    ↓
Stop、Release 或失败清理结束这次会话
```

一组会话资源包括：
```
worker
命令通道
取消令牌
demuxer
decoder
output
pipeline 缓冲与时钟
```
它们共同服务于这一次准备出来的播放过程。
注意几个生命周期并不相同：

| 对象或概念 | 生命周期 |
|---|---|
| `PlayerEngine` | 从创建到整个播放器关闭 |
| factory | 当前随执行器保留，可用于多次 Prepare |
| 播放会话 | 从 Prepare 创建资源到清理完成 |
| epoch | 一段仍然有效的数据和反馈所属的代次 |
| 一次连续播放 | 从 Play 到 Pause 或自然结束 |
同一个会话可以包含多次 Play，也可以经过多个 epoch。
例如 Seek 会切换 epoch，但通常继续使用原来的 worker、decoder和 output。
---

### 2. 用最少的状态表达资源所有权
当前执行器只有两个核心字段：
```rust
struct PlaybackEffectExecutor<F> {
    factory: Arc<F>,
    worker: Option<PlaybackWorkerHandle>,
}
```

可以分别理解为：
```
factory: 创建会话的能力
worker：当前会话的管理责任
```
这两个东西分开很有价值。
Stop 之后：
```
worker = None;
factoty 仍然保留
```

因此，下一次 Prepare 可以重新创建会话。
当前`WavPlaybackFactory`保存的是文件路径，因而重新 Prepare 会重新打开同一份配置指向的文件。现在还有切换
媒体源的公开流程。

`Some(handle)`的含义：
> 执行器持有这个 worker 的管理句柄。
它不保证 pipeline 已准备完成，也不保证 worker 没有失败。资源管理状态和播放状态需要分别解释。

---
### 3. 工厂负责创建，执行器负责管理，worker负责使用
 
当前这三个角色的边界是：
| 角色 | 负责的事情 |
|---|---|
| `AudioPipelineFactory` | 根据媒体信息创建合适的组件，组装 pipeline |
| `PlaybackEffectExecutor` | 安排创建、转发命令、关闭会话 |
| `PlaybackWorker` | 实际操作 pipeline |

工厂接口的构建顺序是：
```
打开 demuxer
    ↓
选择音频轨道
    ↓
根据轨道格式创建 decoder 和 output
    ↓
组装 PlaybackPipeline
```

执行器只需要知道:
```rust
factory.build(epoch, cancel)
```

它不需要知道 WAV 的 chunk 怎么解析，也不需要知道 decoder 的具体类型如何初始化。
与此同时，构建闭包被送到 worker 内执行：
```
Effect 线程保存创建方案
    ↓
Playback 线程创建资源
    ↓
Playback 线程使用资源
    ↓
Playback 线程释放资源
```
这减少了资源在线程间搬运，也让后续有线程使用约束的后端更容易接入。
`Arc<F>` 共享的是工厂。pipeline 本身仍然由 worker 独占，没有因为用了 `Arc` 就变成到处共享的可变对象。
---

### 4. 为什么不让管理器直接控制每个组件
可以想象另一种写法：
```
执行器持有 demuxer、decoder、output
worker 也需要访问它们
Control 又需要读取部分状态
```

这样就容易出现多个地方能启动、暂停、清空和关闭资源。
当前设计把入口收敛为：
```
执行器持有 handle
    ↓
通过命令表达请求
    ↓
worker 独占并操作 pipeline
```

因此暂停与清空的顺序、Seek 时的缓冲处理、自然结束判断，都集中在线程内部完成。
执行器只需要关心三种动作：
```
创建会话
向会话发送命令
结束会话
```
这种设计的收益是：每个组件需要理解的事情更少，出问题时也更容易判断责任在哪一层。
---
### 5. 当前设计的取舍，不必包装成唯一正确的架构
现在的会话管理选择了：
- 同时管理一个播放 worker
- 关闭旧会话后，再创建新会话
- 暂停和自然结束后保留资源
- 播放失败清理会话
- 通过消息和 epoch 处理异步结果
它带来的好处是顺序明确，资源责任集中；代价是旧 worker 退出慢时，新的会话创建也要等待。
对于现阶段，这是可以解释、可以掌握的一组取舍。
将来如果要实现预加载下一首、无缝切换或更复杂的错误恢复，才可能需要多个会话、异步关闭或局部组件重建。到那时再增加结构，并让每个新字段对应一个实际存在的中间状态。
这里所谓的设计“艺术”，就在于：用足够少的机制，把真实存在的状态和责任表达清楚，同时知道这些保证依赖哪些前提。
