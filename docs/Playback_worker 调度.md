## Playback Worker 播放调度
调度可以理解为：
**m每轮先处理控制请求，再推进少量媒体工作；能够继续就马上继续，暂时没有进展就等待。**
它负责把一条长期运行的 pipeline，组织成既能持续播放、又能响应 pause、Seek、Stop 的执行过程。

### 1. pipeline 管数据，worker 管执行节奏
俩者的分工是：
| 组件 | 主要问题 |
|---|---|
| `PlaybackPipeline` | packet 如何进入 decoder，PCM 如何交给 output，背压时保留什么 |
| `PlaybackWorker` | 什么时候执行下一步，什么时候处理命令，什么时候等待或退出 |

例如：
```
pipeline.step()
```
完成一次有限的推进，并告诉 worker：
```
Progress: 本轮有进展
Blocked: 本轮暂时没有进展
DecoderDrained: decoder 已经排空
```
worker 根据这个结果决定下一轮怎么运行。
这样，pipeline 不需要自己无限循环，也不需要关心控制命令通道。
---

### 2. 为什么要“一小步一小步”执行？
假设 worker 的实现是:
```
收到 Play
    ↓
一直解码到文件结束
    ↓
再处理下一条命令
```
那么文件播放过程中，Pause、Seek、Stop 都可能一直排队。
现在采用：
```
检查命令 → 推进一步
检查命令 → 推进一步
检查命令 → 推进一步
```
每次`step()`返回，就是重新检查命令和取消请求的机会。
不过，这种响应能力有一个前提： **每次调用本身不能无限阻塞。**
如果一次`read_packet()`或 decoder 调用长时间不返回，worker 仍然无法在调用中途检查取消标记。`step()`的结构
提供了检查机会，并不自动赋予底层操作可中断能力。

---
### 3. 主循环的顺序体现了优先级

把当前`run()`去掉错误处理，结构大致是：
```
检查取消请求
    ↓
接收一条命令，必要时等待
    ↓
再次检查取消
    ↓
执行命令
    ↓
定期上报播放位置
    ↓
检查是否自然播放结束
    ↓
暂停或 decoder 已排空？
    ├─ 是：进入下一轮
    └─ 否：执行 pipeline.step()
```
这个顺序有几处设计意图。
**命令在媒体推进之前处理。**
本轮已经收到 Pause，就先暂停，不再继续生产下一批数据。
**进度上报在暂停判断之前**
暂停之后仍然可以报告当前位置，调用方就能观察到位置保持不变。
**完成检查在`decoder_drained`的跳过判断之前**
