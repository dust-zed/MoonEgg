## 视频帧和视频解码器的处理

### 1. VideoCodecSession 为什么存在
`VideoCodecSession` 是额外增加的管理层，目的是让解码器和已经交出去的视频帧，都能安全地访问同一个 MediaCodec。

#### 音频阶段为什么不需要这个问题？
原来的音频解码器大致是：
```rust
struct AndroidAudioDecoder {
    codec: NativeMediaCodec,
}
```

`codec` 只归解码器所有。需要修改它时，解码器方法拿着`&mut self`, 自然可以访问：
```rust
self.codec.try_receive()
self.codec.flush();
```
音频数据复制出来后，交出去的是自己的 PCM 数据。那份音频帧后面不再需要访问 MediaCodec。
因此，所有权关系很直接：
```
音频解码器拥有 codec
音频帧拥有复制出来的数据
```

### 2. 视频帧交出去后，仍然需要访问 codec
Surface 视频帧交出去时，实际图像还在平台槽位里。上层拿到的 token，需要在之后调用：
```rust
codec.release_surface_output(token, true)
```
或者：
```rust
codec.release_surface_output(token, false)
```
于是出现了两个访问者：
```
视频解码器： 提交编码包、领取输出、flush
视频帧： 呈现、丢弃、析构时清理
```
它们操作的是同一个 codec。
而且视频帧可能活的比解码器更久。例如管线还保留着一帧，解码器对象先被销毁了，这帧随后仍需要清理。
这就是我们要解决的两个问题：
1. 谁负责让 codec 保持存活？
2. 多个对象如何轮流修改 codec？
`Rc` 解决第一个，`RefCell` 解决第二个。

### 3. `Rc` 提供共享所有权
普通字段通常有一个拥有者：
```rust
let codec = NativeMediaCodec::new_video_decoder(...)?;
```
将它移进解码器后，其他对象不能再同时拥有这份值。
`Rc` 允许多个对象共同拥有一份值。

```rust
let shared = Rc::new(codec);
let another_owner = Rc::clone(&shared);
```
这里没有复制 codec。两者指向同一个对象：
```
shared ─────────┐
                ├── 同一个 codec
another_owner ──┘
```
只要还有一个`Rc`引用，里面的对象就不会析构。最后一个引用析构时，对象才析构。
所以可以让解码器和视频帧各持有一份引用，确保帧清理时 codec 仍然存在。
但是，仅有`Rc`还不能满足我们的修改需求。

### 4. 为什么 Rc 里面不能直接修改
假设：
```
let shared = Rc::new(codec);
```

通过共享引用访问它，一般能取得的是：
```
&NativeMediaCodec
```

当`flush`、领取槽位和释放槽位需要：
```rust
&mut NativeMediaCodec
```

Rust 的普通借用规则是：
> 可以同时有多个只读借用，或者一个可变借用。
多个对象共享一个值时，Rust 无法仅凭某个对象手里的`Rc`，确认其他对象此刻没有访问它，因此不能随意给出`&mut`。
`RefCell`就是用来处理这种"共享对象需要修改内部值"的情况。

### 5. `RefCell` 的作用：运行时检查借用
先用一个普通数字来看：
```rust
use std::cell::RefCell;

let value = RefCell::new(10);
{
    let mut borrowed = value.borrow_mut();
    *borrowed += 1;
}
assert_eq!(*value.borrow(), 11);
```
这里发生了三件事：
1. `borrow_mut()`申请对内部数字的可变借用
2. `borrowed` 在作用域内持有这个借用。
3. 离开作用域，`borrowed` 被销毁，可变借用结束。
`RefCell`仍然执行借用规则，只是把检查放到了程序运行时：
| 方法 | 取得什么 | 借用冲突时 |
|---|---|---|
| `borrow()` | 只读访问 | panic |
| `borrow_mut()` | 可变访问 | panic |
| `try_borrow()` | 尝试只读访问 | 返回错误 |
| `try_borrow_mut()` | 尝试可变访问 | 返回错误 |

例如：
```rust
let value = RefCell::new(1);
let first = value.borrow_mut();

// first 还或者，已经占用了可变借用。
assert!(value.try_borrow_mut().is_err());
drop(first);

// 第一个借用结束，现在可以重新借用。
assert!(value.try_borrow_mut().is_ok());
```
它不会让两个可变访问同时发生，也不会替你等待。它会检查当前借用是否允许，冲突时立即报错或 panic。
`RefCell`本身不提供线程同步能力。我们这里是在同一个播放 worker 内轮流访问。

### 6. 两者放在一起，各自负责一件事
可以先讲核心关系理解成：
```rust
Rc<ReffCell<NativeMediaCodec>>
```
从外到内读：
```
Rc
  多个对象共同保持它存活
RefCell
  每次访问时检查能否借用
NativeMediaCodec
  实际被操作的 codec
```
一次正常操作大致是：
```rust
{
    let mut codec = shared_codec.try_borrow_mut()?;
    codec.flush();
}
// 离开作用域，借用结束
```
等这次借用结束后，另一个对象才能取得可变借用，执行呈现或丢弃。
这里的 `codec` 实际上是一个借用守卫。它活着时，`RefCell` 记录“现在有人正在修改内部对象”；它析构后，借用记录
解除。
因此我们要求：只在一次操作期间借用 codec，不把借用守卫长期保存在视频帧中。
否则视频帧等待期间，解码器也无法继续提交数据。

### 7. 为什么增加`VideoCodecSession`
直接使用`Rc<RefCell<NativeMediaCodec>>`已经能表达上述核心关系。
`VideoCodecSession` 在此基础上，把访问步骤封装成一个统一入口：
```
session.with_codec(|codec| {
  codec.flush()
})
```
它内部负责：
```
申请可变借用
    ↓
执行传入的操作
    ↓
结束借用
```
这样解码器和视频帧都通过同一套规则访问 codec，而不需要各自到处写借用处理。
前面另外加入的`pending_discards`和`cleanup_error`，是为了处理析构时的清理：
- 帧销毁时，如果 codec 正在被借用，暂存丢弃任务。
- 析构不能返回错误，所以记录清理失败，后续正常操作再报告。
这两项可以等到理解`Rc + RefCell`后再看。

这套结构是我们选择的实现方案。采用它，是因为当前帧需要保留清理责任，并且会和解码器共同访问 codec。现在先抓住这一条关系即可：
```
视频帧后续还要操作 codec
    ↓
需要与解码器共同保持 codec 存活：Rc
    ↓
双方需要轮流修改 codec：RefCell
    ↓
把借用和清理规则集中管理：VideoCodecSession
```
