## AAC 概括性介绍

从播放开发的角度，AAC 最重要的知识是： **输入是什么、解码器需要什么、输出是什么，以及数据在时间轴上如何推进**。
整个过程可以先看成：
```
音频文件或数据流
    ↓ 解封装
AAC 压缩包 + 编码配置 + 时间信息
    ↓ 解码
PCM 数据 + PCM 格式 + 时间信息
    ↓ 音频输出
声音
```

### 1. AAC 是压缩编码，播放器最终仍然播放 PCM

AAC 是一种有损音频编码。编码器把 PCM 压缩成更小的数据，解码器再将其还原为 PCM；还原结果通常不会与原始
PCM 完全相同。
对于播放器而言，区别是：

| PCM 输入 | AAC 输入 |
|---|---|
| 知道格式后，可以直接解释采样值 | 必须经过 AAC 解码器 |
| 固定格式下，每个 PCM 帧大小固定 | 压缩包的字节长度可能不同 |
| 可根据采样数量直接计算位置 | 需要结合包边界、时间戳和索引定位 |

AAC 的 **128 kbit/s** 表示每秒压缩数据大约占 16000 字节，不代表采样率，也不代表解码后的 PCM 位深。
解码后可能是 PCM16，也可能是浮点 PCM，要以解码器输出格式为准。

### 2. 先区分“编码”和“封装”
AAC 描述声音怎样被编码；封装描述编码数据怎样存放，以及如何携带轨道、时间和定位信息。
常见组合有：
| 形式 | 常见扩展名 | 播放器如何取得 AAC 数据 |
|---|---|---|
| AAC 放在 ADTS 中 | `.aac` | 根据逐帧头部分出压缩数据 |
| AAC 放在 MPEG-4 容器中 | `.m4a`、`.mp4` | 根据容器中的轨道和样本信息读取 |

因此，支持 AAC 解码，不自动等于支持所有包含 AAC 的文件格式。还需要相应的解封装能力。
扩展名也不能作为最终判断依据，例如`.m4a`中可能保存 AAC，也可能保存其他音频解码。

### 3. ADTS 简单介绍

 ADTS 是 AAC 数据的一种组织方式，基本结构是：
 ```
 [头部][AAC 数据][头部][AAC 数据][头部][AAC 数据]……
 ```
 头部提供帧边界、长度和部分编码参数。播放器或解封装组件利用它，指导本次应该取出多少字节。
 需要了解两个事实：
 - ADTS 头不是 PCM，也不是要送给扬声器的内容。
 - 解码接口是否接收带 ADTS 头的数据，取决于它的输入模式。
有些接口可以直接处理 ADTS；另一些接口要求先拆掉头部，再单独提供解码配置。接入时必须确认接口要求。
如果使用成熟解封转组件，通常不需要自己记住头部的每个位字段。它应该负责识别格式、切分数据和报告错误。

 ### 4. 一个 AAC 包代表什么
解封装组件输出的压缩包，通常包含一个编码访问单元，也就是供解码器处理的一段完整编码数据。不同接口对
`packet`、`sample`、`frame`的叫法可能不同。
尤其注意：容器中的 sample，不一定是你熟悉的“一个 PCM 采样值”。 它往往是一整块压缩音频。
对于常见 AAC-LC 配置，一个编码帧通常对应每声道 1024 个采样值，也就是 1024 个 PCM 帧。

例如 48kHz 双声道：
```
一个编码帧
    ↓
通常对应 1024 个 PCM 帧
    ↓
时长约为 1024 / 48000 = 21.33 ms
```
但不要在通用播放器里写死“每包必然输出 1024 帧”。AAC 类型、配置和解码接口的输出组织方式都可能不同。
还有一个重要区别：
```
压缩包字节数：用于存储、读取和传输
PCM 帧数量：用于计算音频时长
```
两个压缩包分别占 250 字节和 400 字节，仍然可能代表相同的播放时长。

### 5.解码器为什么还需要“配置数据”

仅仅告诉解码器“这是 AAC”，信息可能不够。它还需要了解具体类型、采样率、声道配置，以及相关扩展参数。

AAC中常见的配置名称是：
- ASC：AudioSpecificConfig
- CSD：Codec-Specific Data, 编解码器专用配置数据
 ASC 是具体的音频配置结构；CSD 是解码接口中更通用的称呼。

播放时通常存在两类输入：
```
初始化配置：告诉解码器如何解释后面的数据
压缩音频包：真正要解码的声音内容
```
成熟的解封装组件通常会把配置放在轨道信息中。接入解码器时，应按接口要求传递；例如 Android 可以通过格式中的 csd-0 提供 AAC 配置。
对播放器开发而言，重点是正确传递配置，而不是自己实现配置解析算法。

### 6. AAC-LC、HE-AAC 对播放有什么影响？
把他们理解为 AAC 的不同类型即可：
| 类型 | 播放端主要关注什么 |
|---|---|
| AAC-LC | 最常见的基础类型之一 |
| HE-AAC | 使用扩展工具，最终输出采样率可能与核心编码采样率不同 |
| HE-AAC v2 | 还涉及立体声重建，需要正确识别最终输出声道 |
| AAC-LD / ELD | 偏向低延迟应用，需要对应解码支持 |

无需先研究这些工具如何压缩声音，但需要确认解码器支持对应类型。
更重要的是：不能仅根据文件初始信息，就永久假定 PCM 输出格式。
拿到解码器报告的输出格式后，应确认：
- 采样率；
- 声道数及必要的声道布局；
- PCM 数值类型，例如整数或浮点；
- 数据排列方式，例如交错或平面布局。
只有这些信息正确，才能正确解释 PCM 字节并交给音频设备。相关字段在平台媒体格式接口中有明确描述。

### 7. 时间戳比“读了多少字节”更重要
压缩包通常还带有 PTS，及呈现时间戳。它表示这段音频在媒体时间轴上的位置。
例如：
```
包 A：PTS = 0
包 B：PTS ≈ 21.33 ms
包 C：PTS ≈ 42.67 ms
```
PTS 不是“现在立刻播放”的墙上时钟时间。播放器需要把媒体时间与自己的播放时钟对应起来。
有容器时间信息时，应优先使用解封装组件提供的时间戳。例如 Android 的 `MediaExtractor` 会报告当前媒体样本的呈现时间。

同时注意：
- 时间单位可能是微秒、纳秒，或者某个时间基下的 ticks。
- 不要根据压缩包字节数推算精确时间。
- 不要假定所有媒体时间轴都从零开始。
- 解码的快，不意味着音频已经被设备播放完。
文件读取、解码和实际播放，是三种不同的进度。

### 8. 解码器是有状态的，输入与输出需要分别管理
解码器内部可能有缓冲，因此不能简单理解为：
```
提交一个包 → 立即得到一个 PCM 块
```
实际可能遇到：
- 暂时没有可用输入缓冲；
- 已提交输入，但暂时没有输出；
- 输出 PCM 已就绪；
- 输出格式发生变化；
- 输入已经结束，但还有尾部输出。
其中“暂时没有输出”是正常状态，不应直接当成失败，也不应因此丢弃待提交的数据。

结束时一般要经历：
```
读完压缩数据
    ↓
向解码器提交输入结束标记（EOS）
    ↓
继续获取剩余 PCM，直到输出 EOS
    ↓
等待音频输出队列播放完成
```
输入结束与输出结束是两个独立时刻。

### 9. seek为什么需要同时处理多层状态。
PCM 可以根据固定字节大小直接算偏移。AAC 的包大小可能变化，而且解码器还有缓存，所以 seek 通常包括：
1. 让解封装组件定位到目标时间附近的合适位置。
2. 清除旧的压缩包、解码输出和待播放 PCM。
3. 重置或 flush 解码器。
4. 从新位置继续解码。
5. 必要时丢弃目标时间之前的 PCM，再更新播放时钟。

所以“文件已经定位到 30 秒附近”和“用户实际从 30 秒开始听到声音”并不是同一个完成条件。

### 10. 还有一个影响无缝播放的概念：编码延迟与尾部填充

AAC 编码可能引入前置延迟采样，结尾也可能增加填充采样。完整解码结果中，这些部分不一定属于原始有效音频。
如果需要准确时长、连续曲目无缝衔接，就要根据相关元数据裁掉这些采样。有些框架已经处理，有些需要调用方处理，不能重复裁剪。
