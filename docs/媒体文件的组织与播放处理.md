## 媒体文件的组织

我的理解：
> **容器组织一条或多条轨道；每条轨道具有格式描述和样本序列；每个样本关联数据、时间信息和属性。**

"`track_format + samples`" 可以作为入门模型，但容器还需要记录如何找到样本，以及怎样解释它们的时间关系。

可以围绕三个层次来理解媒体文件。
| 层次 | 回答的问题 | 典型信息 |
|---|---|---|
| 描述信息 | 里面是什么？ | 轨道类型、编码格式、宽高、采样率、声道数 |
| 索引与时间信息 | 数据在哪里，何时使用？ | 偏移、大小、时间戳、时长、同步点 |
| 媒体负载 | 实际处理什么？ | 压缩音频、压缩视频或未压缩数据 |

这些信息在逻辑上属于同一条轨道，在文件中却不一定紧挨着存放。
比如下面是逻辑结构：
```
媒体容器
├── 视频轨道：格式描述 + 时间与索引信息 + 视频样本序列
├── 音频轨道：格式描述 + 时间与索引信息 + 音频样本序列
└── 字幕轨道：格式描述 + 时间与索引信息 + 字幕样本序列
```

而媒体负载文件中可能交错排列：
```
一组视频样本 → 一组音频样本 → 一组视频样本 → 一组音频样本……
```

## Android 如何访问媒体文件

媒体文件保存了轨道描述、时间和索引信息，以及媒体负载。Android 通过 MediaExtractor 解析这些组织关系，
应用不必自己计算每个样本的文件偏移。

其中有两个需要区分的对象：
| 对象 | 作用 |
|---|---|
| MediaExtractor | 打开数据源，发现轨道，选择轨道，读取样本和定位 |
｜ MediaFormat ｜ 用带类型的键值字段描述媒体格式 ｜

MediaExtractor 可以理解为“知道如何访问媒体内容的读取器”；MediaFormat 则是读取器提供的一份“格式说明”。

取得轨道格式不等于读取了该轨道的所有数据，也不等于已经解码。对于 AAC、H.264 等压缩轨道，提取的样本仍是压缩数据。

### 1. 从容器中发现轨道
打开一个媒体文件后，先查询轨道数量，再按索引取得各轨道的 MediaFormat。
例如：
```
轨道 0：视频，H.264，1920 × 1080
轨道 1：音频，AAC，48000 Hz，双声道
轨道 2：音频，AAC，48000 Hz，双声道
```
这里的轨道索引用于区分媒体流。
两条音轨可能是不同语言。它们在同一个容器中，可以共享影片的时间线，但拥有各自的样本序列。

### 2. MediaFormat 描述什么
MediaFormat 不是固定字段全部齐备的结构体。读取时既要知道字段名，也要知道字段类型，并处理字段缺失的情况。
| 字段 | 类型 | 描述 |
|---|---|---|
| mime | 字符串 | 媒体类型，例如 AAC 对应 audio/mp4a-latm |
| sample-rate | 整数 | 媒体采样率 |
| channel-count| 整数| 音频轨道数 |
| width、height| 整数 | 视频尺寸 |
| durationUs| 长整数 | 时长，单位为微秒 |
| csd-0 等| 二进制缓冲区 | 编解码器初始化数据 |

字段与轨道类型有关，不能要求每条轨道都具有采样率、声道数和视频尺寸。

读取字段还需要区分两件事：
- 平台是否提供了这个字段
- 提供的值是否满足当前处理要求。
例如，没有取得时长，意味着时长未知；取得采样率零，则不能作为有效的音频采样率使用。

### 3. 初始化配置与媒体样本不同
AAC、H.264 等编码需要初始化信息，让解码器知道后续数据如何解释。
Android 使用 csd-0、csd-1 等格式字段携带这类 codec-specific data。AAC 使用 csd-0；H.264 通常通过 csd-0 和 csd-1 携带 SPS、PPS。

当配置数据已经放入传给 MediaCodec 的 MediaFormat 时，平台会在启动时处理它，不应再重复手动提交同一份配置。

### 4. 发现轨道与选择轨道是两步
查询轨道格式，用于了解文件中有什么。
选择轨道，用于决定后续提取哪些流的数据。
如果只播放原声，就选择对应音轨；如果播放带声音的视频，就需要选择视频轨道和目标音轨。
选择另一条轨道不会自动取消已有选择。多条轨道选择时，读取器会提供这些已选轨道的样本，因此每次读取都需要知道当前样本属于哪条轨道。

### 5. 围绕“当前样本”读取
 MediaExtractor 对外提供一个当前位置：
 | 查询或操作 ｜ 回答的问题 |
 |---|---|
 | getSampleTrackIndex | 当前样本属于哪条轨道 |
 | getSampleSize | 当前样本有多少字节？ |
 | getSampleTime | 当前样本的呈现时间是多少？ |
 | getSampleFlags | 当前样本属于哪些属性? |
 | readSampleData | 当前样本的数据是什么？|
 | advance | 移动到下一个样本 |

 这些查询应围绕同一个当前样本完成：
 ```
 确认当前样本存在
     ↓
 读取所属轨道、时间、大小和标志
     ↓
 读取媒体字节
     ↓
 保存或交付完整样本
     ↓
 advance
 ```
 如果读完数据就先推进，再查询时间戳，就可能把当前样本的字节与下一样本的时间戳组合在一起。
 
 读取顺序也不能随意按呈现时间重新排序：压缩视频可能存在解码依赖，呈现顺序与解码顺序可以不同。

 ### 6. 从 Android 接口看通用的媒体处理
无论底层采用哪个平台，播放器通常都需要解决这些问题:
| 通用问题 | Android 中对应的能力 |
|---|---|
| 输入是什么 | 设置数据源 |
| 有哪些媒体流 | 查询轨道及格式 |
| 要处理哪些流 | 选择轨道 |
| 当前数据属于谁 | 查询样本轨道索引 |
| 这份数据何时呈现 | 查询样本时间 |
| 怎样取出数据 | 读取样本字节 |
| 怎样继续读取 | 推进当前样本 | 
| 怎样随机访问 | 定位到目标附近的同步样本 |

这就是解复用器对上层提供的主要能力：把容器内部的组织方式转换成“流描述”和“带有归属、时间信息的数据单元”。
不同平台不一定提供完全相同的信息。比如当前这些 Android 提取接口提供 PTS，没有独立的 DTS 查询接口；上层抽象
应允许信息缺失，不能简单把 PTS 复制成 DTS。

### 从具体操作举一反三

#### 场景一、只听视频文件中的声音
只选择目标音轨，提取并解码音频样本，再送入音频输出。
这说明文件包含视频，不代表每次使用它都必须解码视频。容器内容与本次选择的处理路径是两回事。

#### 场景二、在双语影片中切换音轨
需要改变轨道选择，还要协调就音频队列、解码器配置和新音轨的时间位置。
这说明“选择数据来源”知识切轨的一部分。播放器还必须保证新旧数据不会混播，并让新音轨接上当前播放时间。

#### 场景三、跳到第十秒
定位操作通常先找到目标附近的同步样本。对于存在帧间依赖的视频，可能需要从更早的位置开始解码，再丢弃目标之前的输出。
这说明seek不只是改变文件偏移，还涉及解码依赖、队列清理和播放时钟调整。
