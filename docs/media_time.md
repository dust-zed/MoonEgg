## 1. 轨道时间戳：媒体文件里的原始时间
这是 demuxer 从容器中读出的 PTS、DTS、duration。 
它通常由两部分组成：
```
整数 ticks + TimeBase
```
不同的轨道存在着不同 TimeBase

### PTS 和 DTS
轨道时间戳里还要区分：
- DTS: 这个 packet 什么时候应该被解码
- PTS：解码后的 frame 什么时候应该呈现
没有 B 帧时，两者可能相同。有 B 帧时，解码顺序和显示顺序不同。

* demux/decode 管线关心 DTS 和 PTS；
* 视频调度和音画同步最终关心 frame 的 PTS。

轨道时间戳还有几个特点：
* 不一定从零开始；
* 可能是负数；
* 不同轨道可能使用不同 time base；
* packet PTS 不一定严格递增；
* 可变帧率视频不能通过帧序号推算时间。

## 2. 媒体时间：统一后的播放时间线
轨道时间戳不能直接比较：
```
video: 180000 @ 1/90000
audio: 96000  @ 1/48000
```
所以播放器要把他们转换到统一时间轴，例如纳秒：
```
video → 2,000,000,000 ns
audio → 2,000,000,000 ns
```
这就是`MediaTime`.
它回答的是：
> 这一帧位于媒体内容的什么位置？

### 为什么要对齐起点
文件里的轨道不一定同时从零开始：
```
video start = 10.000 秒
audio start = 10.023 秒
```
播放器可以选择 10 秒作为统一 presentation origin：
```
video first frame → MediaTime 0 ms
audio first frame → MediaTime 23 ms
```
这保留了音频比视频晚 23ms 开始的关系。
所以媒体时间的建立通常包含两步:
```
原始 timestamp
    → 按 time base 换算
    → 减去统一 presentation origin
```
媒体时间主要用于：
- 播放位置；
- seek 目标；
- 音视频 PTS 比较；
- 缓冲范围；
- EOS 判断；
- 暂停和恢复后的逻辑位置。

## 3. 系统单调时间：播放器的现实时间参考
媒体时间只说明帧“应该出现在第几秒”，还需要知道“现实中什么时候显示”。 媒体时间和当前播放的帧有关。
这就需要单调时钟，例如 Rust 的`Instant`。
单调时钟与日期时间不同：
* 它只会向前推进；
* 不受时区影响；
* 不受用户修改系统时间影响；
* 不受网络校时影响；
* 适合测量时间间隔和安排 deadline。

播放器会建立一个锚点:
```
anchor_media     = 2.000 秒  // 媒体时间锚点
anchor_monotonic = Instant T0  // 系统时间锚点
```
如果暂停，就冻结当前媒体位置；恢复时重新建立一组锚点。
系统单调时间主要用于：
* 视频帧的显示 deadline；
* 超时；
* 卡顿时长；
* 首帧耗时；
* 播放速度映射；
* 判断某个 frame 是找到还是晚到。
不能使用系统日期时间做这些事情，因为用户校时或 NTP 调整可能让时间突然前跳或后退。

## 4. 音频设备时间：用户实际听到了哪里
音频线程把 PCM 写入缓冲区，并不代表用户已经听到这些时间。
例如：
```
已经写入 AAudio：500 ms PCM
设备实际上播放：380 ms PCM
仍在缓冲区等待：120 ms PCM
```

音频设备时间反映的是实际消费进度，会受到以下因素影响：
* 音频缓冲深度；
* 输出延迟；
* underrun；
* 蓝牙设备延迟；
* 设备切换；
* pause/flush；
* 音频流重建；
* 硬件时钟与系统时钟的轻微漂移。
* 因此在音视频播放器中，通常选择音频作为主时钟。声音不能随意跳过或加速，而视频可以等待、立即显示或丢帧来追赶音频。

## 四者如何协作

完整关系是：
```
轨道时间戳
    │ 解释 PTS/DTS 与 time base
    ▼
媒体时间
    │ 回答内容播放到哪里
    ▼
音频设备时间
    │ 提供实际播放主时钟
    ▼
视频 PTS - 音频主时钟
    │
    ├── 正数较大 → Wait
    ├── 接近零   → Render
    └── 负数过大 → Drop
```
其中系统单调时间负责把音频设备时间、播放锚点和视频 deadline 放在同一个稳定的现实时间参考上。
