### 1. Surface 是什么
在当前播放器场景中, 可以把 surface 理解为：
> Android 提供的图像提交入口，解码器可以通过它把图像交给后面的显示链路。
它自身不负责 H.264 解码。背后有图像缓冲区队列，生产者提交图像，消费者接收并处理图像。
`ANativeWindow` 是这一入口在原生代码中的对应对象，Rust 的`NativeWindow`则包装了它并管理原生引用。
所以这些名字分别处于不同层：
| 名字 | 在当前设计中的作用 |
|---|---|
| Android `Surface` | Android 一侧的图像提交入口 |
| `ANativeWindow` | 原生接口中的窗口对象 |
| Rust `NativeWindow` | 管理原生窗口引用的包装 |
| MediaCodec | 解码视频，并将输出关联到该窗口 |

创建视频解码器时传入窗口，就是告诉 MediaCodec：
> 后面允许呈现的解码图像，要送到这个目标。

### 2. 为什么音频可以马上归还解码器槽位
先理解“槽位”。

MediaCodec 内部维护一组缓冲区。取得输出时，会给你一个索引，例如：
```
输出槽位 3 中，已经有一份解码结果。
现在由应用处理它，处理完后需要归还。
```
这个`3`只是可复用的缓冲区编号，并不是视频的第 3 帧。

当前的音频处理过程是：
1. 取得输出槽位
2. 读取里面的 PCM 字节
3. 将数据复制到 Rust 自己的 Vec。
4. 归还 MediaCodec 槽位。
5. 使用已经复制出来的数据构造音频帧，再交给音频输出。

第 3 步之后，Rust 已经有自己的一份数据，原槽位就可以归还了。
```flow
flowchart TD
    A["AAC 编码包"] --> B["MediaCodec：PCM 输出槽位"]
    B -->|"复制数据"| C["Rust 自己的音频数据"]
    B -->|"复制完成后归还"| D["槽位可再次使用"]
    C --> E["音频输出 → 声音"]

    F["H.264 编码包"] --> G["MediaCodec：图像输出槽位"]
    G --> H["Rust 保留领取凭据，等待同步决策"]
    H -->|"呈现"| I["交给 Surface → 显示链路"]
    H -->|"丢弃"| J["不呈现，归还槽位"]
```

这里有个容易误解的地方：
```rust
release_pending_output(false)
```
在音频路径中，`false`不代表“这段声音不要播放”。
它只表示“不把这个 MediaCodec 输出送去 Surface”。声音数据已经复制出来，仍然会沿音频链路播放。

### 3. 为什么视频不照着音频复制一份
视频也可以采取读取像素、自己保存和处理的路径。我们目前选择 Surface 输出，是为了避免应用把每帧图像读回普通 CPU 内存，
再另外送往现实系统。
Surface 路径中，应用无需取得一份像素`Vec`。Android 也明确规定，配置输出 Surface 后，普通输出缓冲区的字节访问接口
不可用于读取这些图像。
所以 Rust 手中主要保留的是：
```
哪一次领取
这帧的 PTS
这帧的标记
是否已经处理完
```
实际图像仍由平台管理。
这是一种输出路径的选择，并不是“AAC 必须复制，H.264 天生不能复制”。

### 4. 为什么视频槽位要等到呈现或丢弃才归还
假设：
```
音频当前播放到：1.000 秒
刚解码出的视频帧：1.200 秒
```

这帧已经解码好了，但还没到我们准备呈现它的时候。
当前设计会让同步逻辑决定：
| 决策 | 对槽位的处理 |
|---|---|
| 等待 | 保留槽位和 token，稍后再判断 |
| 呈现 | 归还时指定 `render = true` |
| 丢弃 | 归还时指定 `render = false` |

这里的“归还”更准确地说，是应用结束对这次输出的控制：
- `true`: 把输出送到 Surface。
- `false`: 不呈现该输出
指定`true`后，图像可能仍在显示系统中排队或被使用，并不意味着调用返回时已经出现在屏幕上，也不意味着缓冲区立即可被解码器复用。
音频同样需要排队和控制播放时机。只是我们已经把 PCM 复制出来，因此等待发生在自己的音频数据或输出队列中，不必占着 MediaCodec 的输出槽位。

### 5. token 为什么存在
`SurfaceOutputToken`是我们自己设计的类型，不是 Android 要求的类型。
这里有两个字段各有职责：
```rust
pending_output
```
保存真正的平台槽位索引和元数据。

```rust
pending_surface_identity
```
记录“目前交给上层的，是哪一次领取”。

交给上层的`token`带着相同身份，因此归还时可以核对：
```
上层拿回来的凭据
    是否对应
codec 当前仍持有的那个输出
```
这样就不用让上层拿着任意数字索引操作平台。

### 6. 为什么不能只检查索引
因为索引会复用，而 seek 通常还设计 flush。
例如：
```
① 旧帧取得槽位 3，拿到 token A
② 用户 seek
③ codec.flush()：平台收回旧槽位
④ 新帧再次取得槽位 3，拿到 token B
⑤ 管线开始清理旧帧 A
```
如果只检查索引，旧帧 A 可能会错误地归还新帧 B。
Android 规定，flush 后之前取得的输入和输出索引全部失效。
我们增加独立身份后：
```
旧帧：槽位 3，身份 A
新帧：槽位 3，身份 B
```
清理旧帧时，发现 A 与当前 B 不匹配，就只丢弃旧凭据，不调用平台释放接口，也不处理新帧。
所以，槽位索引标识可复用的位置，token 身份标识这一次领取。

### 7. Rc<()> 在这里到底管理什么
它只管理那个“身份对象”。
```rust
let identity = Rc::new(());
```

每次领取都新建一个身份对象：
```
codec 中的引用 ──┐
                ├── 同一个身份对象
token 中的引用 ──┘
```
`Rc::clone`复制的是引用，不会复制图像，也不会创建另一个领取身份。
归还时用：
```rust
Rc::ptr_eq(current_identity, &token.identity)
```
判断双方是不是指向同一个身份对象。`()`的内容没有意义，因此也不需要存储一个数字。
